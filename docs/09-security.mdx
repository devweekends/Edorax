# Security and integrity

**Reads:** [`03-blocks-registry.mdx`](03-blocks-registry.mdx), [`08-data-model.mdx`](08-data-model.mdx)

- **Answers server-side only.** Correct answers, rubrics, hidden tests never leave the server.
  Enforced by the sanitizer (`mdx/sanitize.ts`) + a test that fails if a `correct`, `rubric`,
  `sampleAnswer`, `hints`, or `hiddenTests` key ever reaches a client payload.
- **Grading server-side only** for quiz/test. Client-reported code-check results are trusted by
  design and labeled as such in reports — see [`03-blocks-registry.mdx`](03-blocks-registry.mdx)
  §`<CodeBlock>`.
- **Authorization on every route:** mentors can only touch their own courses; mentees only
  enrolled ones. Centralized in `server/auth/guards.ts` — no ad-hoc checks in route handlers.
- **Gating enforced server-side** — a locked chapter returns 403 from its data loader, not just a
  hidden link. See [`04-progress-and-gating.mdx`](04-progress-and-gating.mdx).
- **MDX is untrusted author input:** raw HTML disabled, component allowlist, no arbitrary imports,
  compiled in a restricted config. Mentors are semi-trusted, but a compromised mentor account must
  not become XSS against every student. See [`02-content-authoring.mdx`](02-content-authoring.mdx)
  §"Rendering pipeline".
- **Rate limits** on submit endpoints (per user, per block) to stop brute-forcing MCQ answers;
  combine with `maxAttempts`.
- **Code sandbox** runs in the browser inside a cross-origin-isolated iframe (Sandpack for JS/TS,
  Pyodide's own WASM isolation for Python — see [`07-architecture.mdx`](07-architecture.mdx)); no
  access to app cookies or the parent DOM.
- **PII:** mentee answers are course-scoped; only the owning mentor and admins can read them.
  Deleting a user cascades responses (`onDelete: Cascade` throughout — see
  [`08-data-model.mdx`](08-data-model.mdx)).
- **AI review is an explicit external transfer.** OpenRouter receives review context only after an
  authorized mentor clicks **Draft with AI**. `OPENROUTER_API_KEY` is server-only. The client sends
  a response ID, never a rubric, reference answer, or learner answer supplied as action input; the
  server reloads and validates those values after `requireMentorOfCourse`. Learner/course text is
  delimited and treated as untrusted prompt content. Submitted URLs are labeled but never fetched.
  Structured output is schema-validated, returned as an editable draft, and cannot update a
  `Response`, create a `Review`, or recompute progress. Only the mentor's separate review submit
  action can do that.

- **Learner AI keys are an explicit external transfer, on the learner's own account.** A learner's OpenRouter
  key is stored only as AES-256-GCM ciphertext (server key `AI_KEY_ENCRYPTION_KEY`, user id as associated
  data), decrypted in memory for one request, and never returned, logged or put in an error. The AI interview
  sends the learner's answers, pasted context and the block's server-only rubric to OpenRouter; learner and
  course text is delimited and treated as untrusted, and replies that repeat the rubric or the system prompt
  are discarded. See [`13-ai-interview.mdx`](13-ai-interview.mdx).

## Quiz integrity and Secure exams (desktop app)

- **Signals, not verdicts.** Integrity notes (focus loss, blocked apps, faces, typing bursts) are flags
  for a mentor. Nothing fails a learner on its own, and the mentor's review is the final call.
- **The server does not take the app's word for it.** In Secure mode the desktop app signs its system
  check (`secure/start`), every heartbeat and its finish message with HMAC-SHA256
  (`services/integrity/app-proof.ts`). The signature covers the attempt, the action, the time and,
  for the system check, every field the server trusts (matched apps, virtual machine, displays,
  camera). The server refuses a missing, wrong or old (about 90 seconds) signature, so a browser
  that copies the request by hand is turned away (`SECURE_APP_REQUIRED`). The key is
  `SECURE_APP_SIGNING_KEY` on the API and `EDORAX_SECURE_APP_KEY` when the app is built.
  Production refuses Secure exams without it.
- **The time limit is checked on the server** for Secure exams: first consent plus the chapter's
  minutes (plus a short grace for the automatic save). Standard mode keeps its limit in the app.
- **Data is kept small.** Only the names of blocked programs that matched leave the learner's
  computer, never the full process list, files or screen. Face checks run on the learner's own
  computer, and camera stills are deleted by the retention job.

### Honest limits

No desktop check is 100% safe. The point is to discourage, detect and document, with a person
deciding.

- The signing key ships inside the app, so a determined person can extract it and sign reports
  themselves. Signing stops the easy bypass, not every bypass.
- A copied report can be replayed for about 90 seconds. Rejecting a used signature needs a stored
  nonce or "last proof time" column.
- While a desktop sitting is alive, answers are accepted from any signed-in session. Tying each
  answer to the app (for example a per-sitting token returned only after a signed start) is not
  done yet.
- A second phone or a helper in the room cannot be seen by any of these checks.
- The consent screen says this to learners in plain words, before the exam starts.

## The sanitizer contract (required test)

`mdx/sanitize.ts` is the single choke point between `Block.config` (server) and what the reader
route sends to the client. Any new block type's config schema must be run through this test before
it ships:

```
Given any Block.config for any registered block type,
sanitize(config) must never include keys: correct, correctOptionId, correctOptionIds, rubric, sampleAnswer, hints, hiddenTests, tests, solution, explanation
```

`explanation` is stripped too because it usually names the right option. The learner still sees it,
but only after answering: the respond route and the saved block state return it with the grade.
Authored short-answer `hints` stay server-only until enough wrong LLM attempts; then one hint is
returned with the grade (never the full `sampleAnswer`).

This should be a property-style test over the Zod schemas in the registry (see
[`03-blocks-registry.mdx`](03-blocks-registry.mdx)), not a hand-maintained list of block types —
so a new block type fails this test by default until its sanitizer projection is written, rather
than silently leaking config.
